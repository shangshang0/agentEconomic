# Agent 本体经济学微观基础：冻结版 0.5

日期：2026-10-25  
版本关系：0.5 在 0.4 基础上明确区分理论地基、通用数学辅助工具、案例机制和实验审计规程，并增加 Authority World v2 的时钟/选举执行模型。两期耦合界归入可复用的概率辅助工具，不计为 agent 本体经济学理论贡献。此次更新不增加经验行为公理，也不引入独立性、平稳性或匿名性假设。

## 1. 地基不以经验行为假设起步

本版本对地基本身的最小承诺、Lean 假设与研究流程的区别，见[地基边界说明](FOUNDATION_BOUNDARY.md)。此处的数学工具和案例模块不等于额外基础公理。

研究对象是计算主体在制度中产生的行动、执行、生产、资源和后续状态。最小形式对象是有限主体集合、主体状态、可观测事件、资源更新规则，以及分别表示响应、制度执行、生产和状态更新的概率核。

这里的概率核是待研究的对象，不是被偷偷指定的规律。理论**不**假设理性、稳定偏好、独立主体、匿名性、对称性、平稳性、固定成功人数，也不假设资源余额普遍决定行动或存活。模型/计算构成、具体条件与制度机制可以分别参数化；数据不足以约束某个核时，理论只给部分识别集，不输出伪精确点预测。

## 2. 数学定义、条件推论和经验限制

| 类别 | 内容 | 是否需要经验验证 |
|---|---|---|
| 定义/表示 | 主体、状态、事件、资源账本；响应、机制执行、生产、转移分层；任意有限人口及身份子集 | 定义本身不以数据“证明”。案例映射需核验日志字段及事件语义 |
| 数学推论 | 有限概率核的组合；账本加总；给定逐事件阈值规则时的路径推论；未约束核下的非识别 | Lean 检查形式推理。前提若映射到案例，另做直接数据检查 |
| 案例限制 | 完整输入/配置固定、某资源触发终止、某响应核跨请求不变、任务层频率可运输等 | 每项都需短小、可复跑的针对性检查；不通过则拒绝该限制，不动地基 |
| 实证结果 | 某次实验中的提议、指派、成功、存活与资源 | 作为案例裁决和反例，不倒灌为普遍公理 |

0.2 中 F1–F7 不是七条关于 agent 行为的公理。它们应作如下读取：F1、F2、F4 是过程/账本/核的形式化表示；F3 是响应和执行的分解，只有“改执行器不改提议律”才是需验证的限制；F5 是可查询任意有限子组的接口及条件等式；F6 是非识别和拒绝点预测规则；F7 是给定即时阈值转移规则后的数学结论。后四类中出现的现实案例前提不能仅靠 Lean 证明。

实验假设的低成本检查、拒绝规则和失败处置属于**研究流程规程**，不是 agent 本体经济学公理，也不由 Lean 理论推出。具体操作记录在 [实验限制登记与拒绝规程](EXPERIMENTAL_MODEL_ADMISSION.md) 和机器登记表中；Lean 验证器可以检查这些记录是否完整，但这种脚本检查不构成理论定理。当前 CTF 没有获准的行为点预测核，原因是现有候选分配—生产规律未通过留出诊断；这属于案例模型裁决，不是地基公理。

## 3. 现有 CTF 案例限制的低成本裁决

脚本 `analysis/validate_case_assumptions.py` 可在不调用模型 API 的条件下，从归档表和已有 pilot 原始记录重建检查；输出 `lean/verification/assumption_validation.json` 与 [逐项假设校验表](ASSUMPTION_VALIDATION.md)，并由 `lean/verify_micro.py` 检查登记完整性并纳入哈希清单。v2 时钟和选举映射另有分别运行的实际后端边界/分支审计，结果与 Lean 源一并哈希登记。

| 拟用限制 | 最低成本验证 | 当前结果 | 理论处理 |
|---|---|---|---|
| 研究流程：案例限制须登记核验与拒绝方法 | 校验机器登记表中的检查、拒绝条件、失败动作；未通过者不得用于当前案例点预测 | 本次 10 项登记；0 项未验证/被拒限制进入案例预测 | 这是案例研究的流程约定，不是 Lean 命题、agent 公理或经济学理论结果 |
| 历史 agent-visible 输入无法重建 | 检查每条归档 gateway exchange 的输入、工具 schema、响应关联和请求签名 | 24 worlds 共 45,180 条完整输入；签名均唯一；与 context index 的关联缺口单列记录 | **输入可重建，不构成障碍**；精确输入无重复，所以只能说同输入响应波动未识别 |
| 事件账本、资源更新和菜单/任务映射忠实于归档 | 逐 world 重放，并与终态和任务事件对账；按 run/day 检查身份键唯一 | 资源账本 24/24 对齐；任务菜单 join 24/24 完整；核验结果均来自事件；405/405 个 world-day profile 均有六个不同身份 | 可用于这批 CTF 案例，不能自动推及别的后端 |
| 能量阈值在所有制度下决定存活 | 对每个 agent-day 比较存活标记、回放余额和制度条件；静态核对后端终止分支 | `world_engine_v2.py` 的 `_deaths` 明确实现：非 symbolic 条件下余额 `<= 0` 即终止；symbolic 条件直接跳过该检查。非 symbolic trace 中负余额观测为 0；symbolic 中日初负余额且仍存活 331 行、日末 354 行 | **拒绝普遍耦合**；代码和 trace 共同支持该 CTF 后端的条件规则，不能推及其他后端 |
| stage-1 的任务层指派频率能预测 stage-2 | 按既有冻结频率逐 holdout world 计绝对误差 | 4/4 单元超过事后 5 个百分点筛查线 | 拒绝该点预测作为当前 CTF 案例规律；这是回顾性诊断，不是预注册显著性检验 |
| 可见资源信号单调改变行动提议 | 同一短 vignette、配对比较两个显示余额，并将原提议离线重放到两个账本 | 已有 pilot：余额 2 时 work 15/20，余额 5 时 20/20；相同 35 个 work 提议在执行重放中分别 0/35、35/35 接受 | 只作该 vignette 的局部诊断。不得写成一般响应公理；更广的规律需新冻结实验 |

以上验证把“简单可检查”落到具体操作：重放、按身份/时间 join、检查阈值反例、对配对 vignette 计数。对无法用短小诊断操作验证的行为不变性或运输性，不把它升级为假设；保持响应/转移核任意，报告无点预测或部分识别。

## 4.1 一个对任意随机机制成立的资源可行性预测

Lean 模块 `lean/AgentMicrofoundations/ResourceSurvivalBound.lean` 现在证明：设一个有限随机结果给出各账户的非负有理余额，统一的正续存准备金为 $d$，令 $S$ 为社会总余额、$N_d$ 为达到该准备金的账户数，则

\[
d k\;\Pr(N_d\ge k)\le \mathbb E[S].
\]

它不要求响应理性、分配匿名、固定成功人数，或主体/任务结果独立；随机分配、生产和转移的任意相关性都可以留在联合结果分布里。该界对任意机制都是资源可行性上限，而且 Lean 同时给出达到等号的可行状态，因此不能仅靠重新分配突破它。它预测的是“资源足以支撑至少 $k$ 个账户达到准备金”的概率上限，不是主体会选择转账或任务的行为规律。

案例使用仍有明确门槛：须从账本核验非负余额，并从执行规则说明 $d$ 对应的实际运行准备金。CTF 的余额非负条件已在非 symbolic trace 中按每个 agent-day 检查，后端阈值也已核对；但后端死亡阈值为零，直接代入 $d=0$ 会令概率界退化。因此，当前不能把本定理冒称为 CTF 的存活人数预测。若要预测“撑过下一次基础消耗/必要调用”，必须先从具体时序和强制扣费规则导出正准备金，再用案例核验；不同任务、机制或计费条件可以有不同 $d$。

## 4.2 不知道跨期相关性时的 persistence 预测区间

`lean/AgentMicrofoundations/TemporalIntersectionBounds.lean` 将“持续存活/活跃/可参与”表示为有限期要求事件的交集。设第 $t$ 期的必要条件为 $A_t$，则在任意有限联合分布下：

\[
1 \le \Pr(\cap_{t=1}^T A_t)+\sum_{t=1}^T\Pr(\neg A_t),\qquad
\Pr(\cap_{t=1}^T A_t)\le \Pr(A_s)\quad(\forall s).
\]

这相当于分布无关的下界 $\max(0,1-\sum_t(1-p_t))$ 和上界 $\min_t p_t$。Lean 证明 `persistent_event_probability_lower_bound`、`persistent_event_probability_le_each_period`，并在 `PersistentEventCase` 中要求案例明确给出“终点 persistence 等价于每期约束都通过”的映射。该映射可由逐期余额/终止规则重放直接检查；若中途复活、重置或存在未记录的宽限期，检查失败，就拒绝此 persistence 实例化。

此结论不要求成功独立、响应平稳、agent 同质或分配匿名。它的经济内容是：边际成功率相同不代表多期存活率相同；若只测得每期边际率，理论仍能给出跨期生存概率区间，但不能从这些边际率点识别数值。`AgentMicrofoundations.lean` 已有三期 Markov 对照，展示相同逐期成功边际可对应不同生存质量。区间下界若小于零则按零截断；区间太宽时须报告“边际信息不足”，不得以独立性补窄区间。

零 API 案例审计选取每个 world 的六个具名 agent、共同 horizon $H=8$，以 world 内有限总体占比为统计对象，而不是随机抽样或 superpopulation 率。24/24 worlds 均无退出后复活；逐日活跃指示的合取与第 8 日活跃比例 24/24 一致；观测 persistence 全部落在无依赖下界/上界区间中，其中 20/24 world 的一般区间恰好收缩为一点，最大宽度为 $1/3$。因为这里以同一条轨迹计算边际与 persistence，这验证的是事件映射、吸收状态及数学界与数据账本的一致性；**它不是事前预测检验，也不说明新 world 的存活率**。CTF 的目标函数、分配和生产核仍未冻结，因此不得把该案例描述统计升级为跨 world 点预测。登记表记录这一状态为 `PASS_DESCRIPTIVE_24/24_WORLD_PATHS`，且 `used_for_case_prediction=false`。

### 实验限制的检查成本记录

实验限制登记表记录 `verification_cost`、检查方法、拒绝规则和失败处置。这些字段只管理案例建模流程；它们不构成经济学命题。两期耦合等通用数学辅助结果另列在 [Lean 辅助工具索引](lean/METHODS_INDEX.md)，不会并入理论索引或作为 agent 行为发现陈述。

这一区分避免把“尚未验证”说成“理论无法构建”：数学地基先在弱前提下推出可用的识别集；经验限制只有存在简单可复跑测试且通过预设裁决后，才可用于缩窄案例预测。小实验也只能支持所测条件与容忍度，不会证明一个普遍行为定律。

对“设置参数是否真的进入模拟”，新增 `analysis/audit_ctf_design_coverage.py` 与 [逐字段覆盖表](CTF_PARAMETER_COVERAGE.md)。它从 Lean 的 `CTFDesign` 声明抽取字段，并要求每个字段在审计映射中恰有一项。当前 46 项中，9 项被资源事件回放直接消费，1 项部分进入任务资源事件，1 项连接人口接口，11 项只参与时钟顺序检查，1 项由调用者单独提供模拟 horizon，23 项仍须绑定到具体案例的条件/机制/生产/运行核。验证器会在字段数或映射漂移时失败；因此“设计记录里有字段”不会被误报为“该字段已影响数值预测”。

另有 `lean/AgentMicrofoundations/CaseStudies/AuthorityWorldV2Clock.lean` 将 v2 后端的每日时钟与机会窗口写成精确有理时间规则：第二天起分配窗口为 `[0, allocationSeconds)`，工作窗口为 `[allocationSeconds, workEndSeconds)`，当选制度在 `registrationOpenSeconds` 起开放登记/投票；任务在 `offeredDay + lifetime - 1` 日结算时到期。Lean 证明分配与生产窗口不相交、工作截止先于注册窗口，并通过冻结配置检查开闭边界和任务寿命。零 API 审计对 8 份 agent-econ v2 配置逐项核验这些时钟边界。

`lean/AgentMicrofoundations/CaseStudies/AuthorityWorldV2Election.lean` 把下一日职位选任写为精确有限映射：输入是存活集合、候选集合、已投票记录和 seed 所决定的缺失票/并列选择；无候选人、全员候选和普通 plurality 三个后端分支分别计算。Lean 推出普通 plurality 分支的当选者必为候选人，并演算了四主体、一张缺失票补入后的 1:1 并列例子。零 API 审计实际调用 Python `_finalize_election` 覆核无候选、全员候选和该并列分支的 reason、补票数与计票结果。这个案例模型可以在给定提名、票和 seed 后精确算出谁任职；它不预测谁会参选或投给谁，因此不是行为核，也不能单独预测 CTF 的分工结果。通用 `CTFDesign` 的字段仍须显式连接到具体 case family。

## 5. 简约的拒绝规则

1. 账本重放、事件顺序或主体/任务 join 不通过：拒绝案例数据映射。
2. 直接反例违反某个案例限制：拒绝该限制。symbolic-energy 的存活记录已足以拒绝“能量普遍控制存活”。
3. 冻结的局部规律未通过预先设定容忍度：拒绝案例核；不得用事后追加变量把它补成成功。
4. 限制缺乏直接测量，或一个小型针对性检查都无法设计：不把限制作为前提。使用任意核、部分识别或明确“不预测”。
5. Lean 证明只表示形式前提蕴含结论；经验适用性只由对应的上述检查支持，二者不能替代。

## 6. Lean 与案例验证边界

Lean 项目继续验证主体/机制分层、有限动态组合、资源账本、阈值路径、群体查询和非识别等数学结果。新增的零 API 审计不把 CSV 观察变成公理；它只自动判定哪些**案例限制**可用、哪些已被反例或预测误差拒绝。验证清单记录代码、数据、理论版本及审计输出的哈希，供第三方复跑。
